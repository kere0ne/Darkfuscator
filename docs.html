Quick start

Darkfuscator compiles readable Luau into encrypted custom bytecode that runs inside a proprietary VM embedded in the output file. The output contains no Lua source and no Lua bytecode for a decompiler to read: it is a serialized instruction stream, encrypted, packed six bits per character, and decoded at runtime by an interpreter whose handlers are one table slot each.

luau-obfuscator script.luau script.protected.luau --preset maximum

Or open the web UI, paste your script, and press Protect. Both paths produce the same kind of build; the UI always uses maximum.

Installation

The tool is dependency-free JavaScript. To run the CLI you need Node 18 or newer:

git clone https://github.com/kere0ne/Darkfuscator
cd Darkfuscator
node bin/luau-obfuscator.js --help

The web UI needs nothing installed: open site/index.html directly, or host the site/ folder on any static host. Cloudflare Pages deploys it as-is (no build command, output directory site).

CLI usage

luau-obfuscator input.luau output.luau --preset maximum

With no output path the file is written next to the input as input.protected.luau. A deterministic build repeats the exact same output for the same seed:

luau-obfuscator input.luau out.luau --seed 1337

Individual knobs override the preset, and a JSON config file can carry them all:

luau-obfuscator input.luau out.luau --config cfg.json --seed 1337

Web UI

The UI is a single glass shell with a sidebar: Obfuscator and Docs on the left, a two-pane input/output workspace, and a statistics strip (protos, opcodes, bytecode bytes, payload chars, size, time, junk statements, seed). There is no settings panel by design: protection is always maximum. Files load by button or drag-and-drop; output copies or downloads with one click; Ctrl/Cmd+Enter runs Protect.

VM architecture

The runtime is a register-based interpreter. Every build generates:

  • A private opcode map. Each opcode in the set gets a fresh random 16-bit id; dead ids fill the dispatch so lifted handlers do not map one-to-one onto real ones.
  • One handler per table slot. There is no single switch to read: control flow only exists in the dispatch chain and inside the handlers, each wrapped in provably-dead opaque predicates that vary per build.
  • Multiple bodies per opcode. The same semantics are emitted in several different bodies and dispatch picks one per call, so a recovered interpreter can never be matched against a single form.
  • An environment-derived seal. At level 1+ the unseal key is not a constant in the file: the audit computes it from environment probes. A static extractor or a replay environment that fakes any probe derives the wrong key and unseals the payload into garbage, with no signal about which probe disagreed.
  • Nested builds. At two layers, the first build's source is compiled again into a second VM with its own map and seal; a dumper peels both to see anything.
  • Self-erasing decode state. The payload, alphabet, checks and decoder slots are nilled as soon as they are consumed; a deferred re-audit one scheduler step later destroys interpreter material if the environment changed mid-run.

Every operation is carried out by a native Luau operator, so metamethods, coercion, integer semantics, coroutines, pcall and error messages behave exactly as they do in the original script.

Bytecode format

The serialized program is a byte stream: zigzag variable-length integers (so jump offsets can go backwards), constant pools per proto with typed tags (nil, boolean, number, encoded string), nested child protos, and instructions as opcode id plus A, B, C operands plus an optional extended list. Strings are stored encoded and only decode through a metatable the first time a handler reads them, so a dump of the decoded program no longer reveals string literals.

The stream is encrypted with a per-build additive key, an XOR keystream, and the environment seal, then packed six bits to the character over a per-build alphabet. Two independent checksums over the decoded bytes guard integrity; a mismatch silently poisons the payload instead of raising a patchable error.

Security model

  • Anti-tamper. The finished build is split into chunks, each encrypted with its own key, and a wrapper verifies the client (DataModel properties, LocalPlayer, services, engine data types, environment identity, write persistence) before decrypting, loading and running it. RunService's Heartbeat re-runs the battery every half second, so a hook installed mid-run is caught too.
  • Anti-dump. Decode material is destroyed as it is consumed, string constants decode lazily, and the deferred re-audit wipes interpreter slots if the environment turns hostile mid-run.
  • Anti-env. The audit runs before the payload is decoded: stubbed builtins, proxy environments that do not persist writes, and injector toolkits over fake DataModels all fail closed, and the program refuses before a single byte is decrypted.
  • Silent failure. Detection paths scramble the seal or wipe material quietly. There is no branded, patchable error string to grep for.

Examples

The tests/corpus/ directory holds runnable example scripts covering variables, functions, closures, tables, loops, conditionals, arithmetic, calls, returns, varargs, and Roblox-shaped API usage. tests/run.js obfuscates each one and runs original and obfuscated side by side through the real Luau VM, comparing stdout, exit codes and resulting global state.

node tests/run.js          # full suite
node tests/fuzz.js 20      # randomised option soak

Performance

Protection and speed are a dial, not a switch. Lightweight keeps overhead near the original; balanced is suitable for live gameplay code; maximum is for code whose protection matters more than a few percent of runtime. Compilation is fast at every level (a few seconds for a 5 KB script at maximum). Output size grows with junk level; lightweight builds stay small, maximum builds land near a megabyte by design.

Limitations

  • Client-side protection is strong but not absolute: anything that runs on a client's machine is ultimately inspectable there. These layers raise the cost of analysis sharply; they do not make it impossible.
  • The anti-tamper wrapper uses loadstring (or load) at the outermost layer only. The bytecode VM core itself never does: the interpreter decodes and executes its own instruction stream directly.
  • Scripts that rely on exotic Luau features the compiler does not model are reported as VMCompileError rather than silently mis-obfuscated.
